# 玩家目标与组卡模型前置设计

状态：2026-10-01 设计审计。现有 BoxLens / MoeNotes 实现保留为未提交 PoC；本文件不表示上线方案已经批准，不启动新的业务实现。先确定真实目标、规则与输入，再决定模型和搜索。

## 先把玩家的目标分清

玩家说“活动排名”，不能默认解释为累计活动 pt。现有 2026-09-30 官方补充公告捕获明确区分：该活动没有累计活动 pt 排名，排名采用歌曲分数。原始公告与最新变更由 root 继续核验；未完成前不声明当前活动的所有排名细则已经确认。

因此，“活动排名冲分”和“活动奖励 / pt 收集”必须是两个目标。日常冲分、稳定过线、跳过刷取、撃奏和有限资源培养也不能共用一个“综合力最高”按钮。

| 玩家目标 | 应最大化 / 最小化的量 | 推荐成立前要确认的真实规则 | 必需的额外玩家输入 | 玩家应看到的结果 | 现有模型边界与前置决定 |
|---|---|---|---|---|---|
| 日常冲分 | 指定歌曲、难度、模式和打法条件下的分数；明确是期望、低分位还是单次最高分 | 该模式可用动作、歌曲加成、技能、结算与随机机制；榜单是否存在及记录规则另核 | 当前培养与普通技能；歌曲 / 难度；理论打法或实际判定记录；参选 / 队长偏好 | 五个物理槽、第三槽队长、对应留影；条件分数范围；相对当前队伍改善；候选 / 已证明状态 | 可计算声明条件下的 native Live。当前有限随机根分布未知，AP 不等于玩家实战；不能把最幸运一局或人为最佳技能顺序当成玩家可执行方案 |
| 活动歌曲分数排名 | 与当期榜单实际登记的歌曲分数指标一致 | 官方公告当前指向歌曲分数排名；仍需核实哪些歌曲、难度 / 模式、单曲还是合集、最佳记录还是其他汇总、并列处理、活动时间、挑战限制及失误 / 断线结算 | 指定活动与目标榜；对应歌曲和难度；报名 / 解锁 / 挑战资格；实际可用次数与打法 | 每个适用榜单的可照摆队伍、可登记分数的模型条件与缺口；不拿活动 pt 冒充排名分 | 与 `clientEventPoints` 分开。当前模型能评估部分分数机制，但不能仅凭已有通用 score 指标推导当期真实排名名次；最新原始规则待 root 核验 |
| 活动 pt / 奖励收集 | 根据玩家意图选择每次 pt、每单位消耗 pt、每分钟收益或目标奖励进度 | 当期 pt 计算、评级、活动加成、消耗倍率、计数 / 窗口、挑战点转换和奖励来源；多个目标的消耗需同口径比较 | 实际活动计数、剩余资源、倍率选择、已取得奖励、时间预算；多人场景还需结果条件 | 每次客户端 pt 预览与明示消耗；若选择效率目标，显示同口径比值和必要假设；无法核实的服务器奖励不承诺 | 当前 `clientEventPoints` 是客户端每局预览，尚不是排名目标，也不是资源效率 / 多局调度器。`conditionalClientEventItems` 需要明确奖励行，不能预测服务器所选掉落 |
| 稳定达标 / 安全过关 | 达到指定分数、评级或任务条件的概率；玩家可另选保留血量、失败率或较小欠分 | 分数门槛与评级表；失败 / 重试 / Continue 的真实判定；目标是结算血量还是全程不失败 | 指定门槛；实际判定记录或经确认的多个打法场景；是否允许重试 / Continue；对低分和失败的容忍度 | 明确的达标条件、欠分与条件分布；若只有 AP 试算，标为理论达标比较 | `scoreAtLeast` 只反映给定判定流与随机根条件的分数达标；`cappedScore` 可用于欠分效用。`scoreAndLifeAtLeast` 只验证结算分数和结算血量，不证明从未归零，也不预测真人发挥。实战成功概率需要额外打法分布和失败流程证据 |
| 跳过演出 | 跳过分数、确定性评级、客户端 pt 或已明确的刷取效率 | 当前模式是否真实允许 Skip；门票 / 消耗、评级和奖励规则；不能把未允许的模式列为可操作建议 | 当前卡片与玩家加成；歌曲 / 难度；目标门槛；实际门票、消耗与活动状态 | 跳过分数 / 门槛结果和所需消耗；与演出队伍分开展示 | Power / Skip 不依赖普通演出技能顺序；对应技能不应成为该目标的无意义必填项。已检查域内的单调分数 / 阈值可使用现有 exact canonical 快路；pt / 奖励和效率不自动继承这个证明 |
| 撃奏冲分 / 多人表现 | 必须先选择最终分数、区间任务、排名条件或活动收益，不能把“开启撃奏”当完整目标 | 模式是否强制撃奏；任务、Just 区间、幸运、排名与冻结快照；多人确认的到达 / 应用机制；实际榜单规则 | 撃奏技能；对应模式和歌曲；判定 / 帧条件；Solo 或明确多人假设。多人结果时间线不由卡池截图取得 | 最终条件分数、区间表现、条件名次与依赖外部输入；显示原生随机机制下的物理队伍 | 现有模型支持有限根分布下部分撃奏机制。Battle / Arena 的输入排名是外部条件，不是由玩家卡组预测出来的真实对手排名；不能默认 Solo 第一。当前 JP 缺 Arena 行不能以 synthetic 验证替代线上可用性 |
| 有预算的培养建议 | 在玩家给定资源和偏好约束下，提高指定目标，或以最小消耗达标；输出成本 / 改善的 Pareto 选择 | 每种升级 / 特训 / 卡阶 / 技能 / 道具 / 角色等级 / 回忆的合法状态转移、材料成本、前置解锁、资源共享和购买限制 | 当前状态、所有相关材料 / 金币 / 票数、可用转换、预算；可升级的范围；不可消耗的稀缺物；真实目标与时间范围 | 当前队伍与具体升级步骤；逐资源成本、剩余预算、收益和替代方案；避免“全部满级”结果 | 现有请求不支持培养预算搜索；不能先用满级队伍再补一个成本数字。须先核状态转移 / 成本表，再设计联合培养与组卡搜索。对角色等级 / 道具等全局升级，要评估它对全部候选的影响 |
| 仅查看综合力 | 当前培养与指定歌曲 / 模式加成下的综合力 | 属性、标签、队长、留影连携、玩家全局与场景加成 | 当前培养、玩家全局状态；可选歌曲 / 场景 | 综合力和加成条件，可照摆队伍 | 可以作为玩家明确选择的独立目标或搜索候选来源；综合力候选不等于演出 / 活动最优证明 |

“单次最高分”和“期望分数最高”也不同。若榜单记录最高一局且玩家准备重复挑战，目标可能是指定次数内的最佳登记分数或达到目标记录的机会。它需要核榜单规则、次数预算、局间随机独立性与打法变化，不能直接把单局均值乘次数，也不能无条件沿用单局达标概率。

## 输入应按目标需要收集

| 信息 | 当前清晰卡池列表截图能否取得 | 正确的后续处理 |
|---|---|---|
| 卡片身份 `(kind, master ID)` | 可识别已观察且匹配当前图库的成员 / 留影；不能证明未见卡不存在 | 保留原图、定位框、图库 / 模型版本和来源；误识别可改身份 / 明确删除，漏卡可补录；无法确定时不编造 ID |
| 等级 | 仅等级视图实际可读的值 | 其他能力 / 百分比视图不转换成等级；裁切、拒识和冲突保留未知 |
| 卡阶 | 图标完整且匹配通过时可读 | 不从稀有度或卡面推断；卡阶 0 模板是拒识用途，不输出合法已拥有 Rank 0 |
| 成员特训次数 | 仅特训视图实际可读的值 | 不从等级上限、另一张卡或默认值推断；当前契约 1–5 不擅自换算成自然计数 0–4 |
| 普通 / 撃奏技能等级 | 当前列表识别链不能取得 | 活跃目标需要哪类技能就补哪类；Power / Skip 不强迫填写未参与计算的技能。选目标后才生成缺失清单 |
| 全部角色等级、乐队道具、VIP、回忆 | 当前卡池列表不能取得 | 使用已有可靠玩家数据、专门截图或人工填写；基础状态只能是明确的试算条件，不标成实际玩家事实 |
| 完整持有集合与完整截图覆盖 | 不能取得 | 玩家可声明完整，或选择仅在已核对的观察子集推荐；子集结果不得标为全账号最优。声明和模型识别事实单独保存 |
| 当前活动计数 / 消耗 / 排名资格 / 剩余资源 | 当前卡池列表不能取得 | 按目标请求对应信息，活动时钟 / 资格 / 排名规则由最新规则源核对；不复制 mock 或其他活动数据 |
| 真人打法、错误分布、对手、网络排名、随机根总体 | 不能取得 | 理论条件、实际记录与外部假设分开；不知道就保留未知，不能从卡池规模或几张高分图估计真实成功概率 |
| 实际培养预算与材料成本 | 截图链目前不能取得 | 预算由玩家提供；成本由版本匹配规则取得。缺任一部分不输出具体花费方案 |

现有客户端、模型和 OCR 都不是“所有字段必须填完”的理由。必填集合应来自已选目标的计算依赖：例如普通演出需要普通技能，撃奏开启才需要对应撃奏状态，Skip 不使用演出技能随机顺序。未使用字段保持未知，不能为了满足类型结构而写入 Rank 1 / 满级并把它保存为真实值。

## 持有事实与搜索卡池必须分开

以下三个动作不是同一件事：

1. “这张图认错了 / 这张卡并非我的持有”：修改观察与持有事实，记录身份修正证据。
2. “我拥有这张卡，但这次不想使用”：保留 owned 集合，用搜索约束排除。
3. “我拥有它，但培养值还没填”：保持持有事实；补字段，或明确只在已核对候选中推荐并标注搜索范围不完整。

当前 PoC adapter 把导出候选卡池和 `ownedMemberCardIds / ownedSupportCardIds` 强制逐项一致，页面排除会同时收缩持有集合。正式设计不能照搬此耦合：回忆计数会读取 owned 集合，删掉“拥有但不参选”的卡可能改变全部候选的综合力。需要独立的持有 / 回忆事实、可评估候选和搜索约束。不能以“已确认完整持有”的全局复选框掩盖这种语义差别。

## 确认应防止错误推荐，而不是制造重填负担

推荐成立的检查顺序：

1. 明确区服、活动 / 场景、真实玩家目标及选曲，绑定 master、谱面与模型版本。目标暂时不支持时先说明缺什么规则，不让玩家白填完整卡池。
2. 上传与补图后保留观察、冲突、覆盖范围；合并去重不得消除分歧。同名文件不代表同一来源，新增截图不能静默覆写之前人工核对。
3. 只列当前目标真正缺少的输入。对错误身份、未知培养与低置信度提供原图定位和可纠正入口，显示“尚缺哪项、哪种页面可以补”。
4. 分别确认持有范围、实际培养事实和用户主动选择的试算假设。不要用一枚总复选框把原始观察、未填技能、完整账号覆盖和示例随机分布都升级成事实。
5. 执行之前保存这次目标 / 卡池 / 玩家状态 / 假设的不可变快照。改卡、换歌、换目标、追加截图或改变活动规则后，旧推荐立即失效；迟到回复也必须绑定旧输入版本。
6. 结果分层显示：实际当前状态 / 条件试算 / 子集推荐；候选排名 / 已证明排名；客户端预览 / 已核服务器规则。让玩家能直接摆五槽与留影，同时理解推荐适用于什么条件。

“只在已核对的卡中推荐”是可以设计的快速入口，但它必须保留完整 owned / 回忆事实，并解释可能漏掉更强的未评估卡。基础培养、示例随机根、假设多人名次只能生成带条件的比较结果。若关键未知会影响当前推荐排序，不能给出不带条件的“你的最强队”。

## 写模型 / 搜索前的决策门槛

| 决策 | 已知 | 仍待核实 / 决定 | 未通过时允许交付什么 |
|---|---|---|---|
| 当期活动排名目标 | 已保存官方补充指向歌曲分数排名，不存在所述累计 pt 排名 | 最新原始公告、活动 ID / 窗口、参赛歌 / 难度、榜单汇总、记录 / 并列 / 次数规则由 root 核 | 规则缺口与来源，不能上线“活动 pt 排名推荐” |
| 单局评分域 | 离线 1.0.1-25 原生单元及现有 solver 有版本化证据 | 当前区服 / 二进制 / 补丁等价与真实整局录制边界；不同目标是否涉及失败、断线或服务器处理 | 声明域内条件计算；不称当前线上整局完美还原 |
| 稳定目标 | 已有条件分数达标、欠分效用、结算血量效用 | 真人打法分布、全程失败规则、重试目标；用户想要哪个风险口径 | AP 或给定判定流下的条件比较，不称真人通过率 |
| 活动资源目标 | 已有客户端 per-atom pt / 条件奖励预览 | 真实消耗、效率分母、服务器奖励和多局状态转移 | 一局客户端预览；不承诺现实奖励或长期最优策略 |
| 截图输入范围 | 身份 / 等级 / 卡阶 / 可见特训及冲突契约已定义 | 新布局 / 降质覆盖、完整持有声明、哪些目标允许子集；未知全局状态如何补 | 观察集合和缺失清单；不推断全持有、满养成或零回忆 |
| 搜索输出语义 | 五槽、第三槽队长、paired Snap；候选搜索与条件穷尽的区别已定义 | 不同玩家目标的排序、并列、次数效用和允许动作；规模 / 时间预算真实测量 | 已精确评估的候选与边界；不能把快速候选叫全局最优 |
| 培养计划 | 当前状态的评分可作为转移后的评估器 | 版本化成本 / 转移图、共享资源、不可逆动作、预算和多目标偏好；联合搜索证明 | 需求清单 / 设计，不产生可执行花费建议 |
| 前端计算路径 | ONNX 网络与 Rust / Worker PoC 的技术边界可测 | 完整浏览器识别链、数据授权与版本更新、延迟、兼容性和本地 / 远端选择 | 技术可行性 PoC；不是玩家目标已正确或业务可上线的证明 |

推荐最优性、模型与游戏一致性、OCR 正确性、输入完整性是不同证明。组件复用、80 个测试和截图到结果 E2E 验收可以证明特定实现路径可运行，不能替代上述规则和目标决策。
